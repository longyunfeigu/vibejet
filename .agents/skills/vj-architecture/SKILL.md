# 架构设计

和用户一起做出会长期约束系统的技术决策，写成 `docs/project/architecture.md`（用户可指定其他路径）。
你负责结构化思考和架构知识，用户负责业务领域和产品取舍。

## 模式

| 模式 | 适用 | 产出章节（见 `architecture.template.md`） |
|------|------|------|
| 快速 | MVP、原型、小功能、技术评审 | 1 架构概述、2 分层架构、7 技术选型、9 附录 |
| 标准 | 中型项目、常规迭代 | 1-4、7、9 |
| 完整 | 大型系统、新项目启动、架构评审 | 全部 9 章 |

用户指定就用指定的；否则收集完背景后推荐一个。

## 1. 准备

- 读 `architecture.template.md`，输出结构以它为准。
- 有 PRD（默认 `docs/product/requirements.md`）就读，重点看它的 Architecture Handoff；没有 PRD 且
  描述不足以支撑决策时，建议先跑 `vj-product-requirements`，用户坚持就只做快速模式并把未定项标为假设。
- 读现有约束：`AGENTS.md`、`pyproject.toml`、`package.json`、`backend/pyproject.toml` 的
  import-linter 契约。仓库已经定下的分层（DDD + 六边形）和技术栈是硬约束，不重新讨论。
- 已有架构文档时默认增量更新：用户已说明要更新就直接做；只有"增量补充 / 章节更新 / 全量重写"
  的选择会改变保留内容而意图又不清时才问一次。不直接覆盖；格式认不出来时先读全文提取现状，
  确定全量重写时把旧文归档到 `docs/archive/`。

## 2. 背景

先弄清系统类型、用户和数据规模、团队熟悉或必须避开的技术、需要集成的现有系统；标准及以上再问
可用性、合规安全、性能基线。能从 PRD 和仓库推断的不问。

## 3. 决策

按模式覆盖这些类别：整体架构风格；分层与目录结构；业务模块划分、职责与依赖（标准+）；数据架构
（标准+）；API 与认证授权（标准+）；安全架构（标准+）；部署架构和可观测性（完整）。

- 每个决策点给选项、权衡和推荐理由。只有一个合理方案或仓库已定的，直接采用并写理由。
- 多个强方案会改变长期边界时，先全部分析完，汇总成一张决策表，用 `ask_user` 一次确认，不逐项审批。
- 具体技术选型用 `web_search` 核对官方当前稳定版本、兼容性和维护状态；网络不可用就用已知稳定版本，
  并在选型表标"版本未在线验证"。
- 每个重大决策后检查它连带要求的其他决策，在对应章节接住。
- 无人值守时重大决策按最合理假设写，标 `Confidence: H/M/L`，集中列入"假设待审批"。

## 4. 写文档

把决策填进模板对应章节。图默认用 Mermaid（架构全景、分层、部署；标准+加时序图）。

架构文档只写模块划分、选型和约束。端点级 API 合同、表级 schema、Screen/Route 合同分别由
`api-design` / `data-model` / `vj-work`（做完一份计划后）写到 `docs/project/api|data|ui/`，这里不重复维护，
否则两份会漂移。

写完检查：按模式应有的章节都有实质内容；每个选型有版本、理由和备选；选型之间没有版本冲突；
分层和目录结构对得上；部署和服务清单对得上；环境变量已列出。

## 5. 审查

文档写完用 `doc-review` 独立审查：表述类意见直接改，改变架构取舍的意见交给用户决定；用户可说"跳过审查"。`docs/project/` 不可写时
先建目录，仍不行就把全文输出到对话请用户定路径。
