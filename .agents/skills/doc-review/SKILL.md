# doc-review — 文档独立审查

作者看不见自己的盲区；不带上下文的审查者更容易发现漏掉的场景和互相矛盾的地方。但文档里写的是
用户的决策，审查者只能提意见，不能替用户改决策。

用户说"跳过审查"就不跑。文档只改了几处措辞时也不必跑。

## 1. 选审查者

**默认：独立代理。** 用 `spawn_agent` 派一个代理，只给它文档路径、下面的审查维度和输出格式，
不给本次对话的上下文。没有子代理能力时，在主上下文里换成审查者视角逐条审，并在摘要里注明"非独立审查"。

**Codex：只在用户要求时用。** 用户终端里的 `codex` 是带代理设置的 alias，后台 shell 不会继承，
所以要通过交互式 zsh 调用；不要写死 `-m`（账号不一定支持指定的模型），也不要加已删除的 `--full-auto`：

```bash
zsh -ic 'codex exec -s read-only --skip-git-repo-check "<审查指令>"' < <文档路径>
```

文档从 stdin 传入，会作为 `<stdin>` 块追加在指令后面。先用 `zsh -ic 'codex exec -s read-only
--skip-git-repo-check "Reply with exactly: OK"'` 探测一次（冷启动约 30 秒）。探测或正式调用失败、
超时、报错时不重试，告诉用户原因，改用默认的独立代理。

## 2. 审查维度

按文档类型选：

- **PRD**：核心场景和边缘场景是否覆盖；异常流、极端输入、并发；用户旅程是否有断裂；需求是否可测试、无歧义；需求之间是否矛盾；非目标是否被需求违反。
- **架构**：组件职责和边界；依赖方向、有无循环；单点故障、级联失败和降级；与仓库现有架构（`AGENTS.md`）是否一致。
- **API 契约**：命名和响应格式是否一致；错误码是否覆盖异常场景；写操作的幂等；向后兼容；鉴权和输入校验。
- **数据模型**：冗余和范式；查询模式有没有索引支撑；跨表一致性约束；迁移与回滚。
- **技术方案**：可行性；风险与缓解；备选方案和取舍；步骤能否执行；回滚路径。

## 3. 审查者的输出格式

```
[N] [Blocking|Non-blocking] [表述|决策] 问题 → 具体修法 | 证据：文档原文（≤30 字）
```

- Blocking：照着做会出事故、丢数据、出安全漏洞，或根本无法实现。Non-blocking：补漏、消除歧义。
- 表述：措辞不清、漏了边界说明、前后数字不一致、写法不可测试——不改变任何人的决定就能修。
- 决策：要增删功能、改变范围、改变用户可见行为或改变产品/技术取舍。
- 只报真问题，引不出原文证据的不报；没有问题就只回"无问题"。

## 4. 处理意见

- **表述类**：Blocking 直接改；Non-blocking 确实消除歧义或补漏才改。改动处标
  `<!-- doc-review: applied [N] -->`。
- **决策类**：不论级别都不直接改，合并成一次 `ask_user` 让用户决定，确认后再改；调用方 skill 有自己的拍板环节时
  （如 PRD 第 7 步），交给它一起问，不单独再问一轮。审查者的意见不能
  绕过用户已经确认过的范围和取舍（比如 PRD 的三桶确认）。
- 明显是审查者误解（没看到完整背景）的意见跳过，并写明原因。
- 文档有机检脚本的，改完重跑（如 PRD 跑 `vj-product-requirements/scripts/validate_prd.py`）。

## 5. 摘要

```
文档审查完成（审查者：独立代理 / Codex / 非独立审查；N 条，X Blocking）
✅ 已改：[N] 问题 → 改了什么
❓ 待你决定：[N] 问题 → 审查者建议
⏭️ 已跳过：[N] 问题 → 原因
```
