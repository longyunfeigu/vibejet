

### 1. 等价类划分法
适用场景：输入项有明确范围、规则，或接口有大量参数时，用于精简测试用例。
核心思想：将输入数据划分为若干个集合，假设集合内的每个数据对发现缺陷的概率等效。验证集合内的一个典型值，即可代表整个集合。

*   有效等价类：符合业务规则的合理输入（用于验证核心功能）。
*   无效等价类：不符合规则的非合理输入（用于验证容错和异常捕获能力）。

实战案例：接口入参校验
需求：注册接口，要求用户名长度为 6~12 位的字母或数字。

| 划分维度 | 有效等价类 (必测) | 无效等价类 (易漏测点) |
| :--- | :--- | :--- |
| 长度 | 6-12位 (如：8位) | <6位 (如：5位)、>12位 (如：13位) |
| 字符类型| 纯字母、纯数字、字母+数字 | 包含特殊字符(如 `@`)、全角字符、中文字符 |
| 数据类型| 字符串 | 空字符串 `""`、`null`、未传该字段、纯数字整型 |

研发视角的延伸：在编写校验逻辑（如注解、正则或条件判断）时，需确保上表中的“无效等价类”均被拦截，防止异常数据穿透到底层引发空指针或 SQL 异常。

### 2. 边界值分析法
适用场景：作为等价类划分的补充，多数缺陷往往集中在输入域的边界。
核心思想：聚焦于输入范围的边界情况。重点测试：等于边界、略大于边界、略小于边界的值。

实战案例：促销满减活动
需求：订单金额满 100 元，减 20 元。

*   常规测试：150元（触发），50元（不触发）。
*   边界值测试：
    *   `99.99` 元 （测试浮点数精度、以及 `<` 和 `<=` 的差异）
    *   `100.00` 元 （精准命中边界，验证临界条件）
    *   `100.01` 元 （刚突破边界）

研发视角的延伸：注意代码中 `>` 和 `>=` 的精确使用；防范分页查询中的数组越界（如 `index=0` 和 `index=length-1`）；警惕时间边界（如 `23:59:59` 到跨日的处理）。

### 3. 判定表法
适用场景：业务逻辑包含多个条件组合，且不同组合会触发不同动作。
核心思想：将所有条件和对应的动作以表格形式穷举，防止逻辑分支遗漏。

实战案例：修改密码校验逻辑
需求：修改密码时，需满足：1. 旧密码正确；2. 新密码符合规则；3. 新旧密码不能相同。

| 规则 | 旧密码正确 | 新密码合规 | 新旧不相同 | 预期结果/动作 |
| :--- | :---: | :---: | :---: | :--- |
| 1 | 是 | 是 | 是 | 修改成功，返回成功标识 |
| 2 | 否 | - | - | 拦截：提示旧密码错误 |
| 3 | 是 | 否 | - | 拦截：提示新密码不合规 |
| 4 | 是 | 是 | 否 | 拦截：提示新旧密码不能相同 |

研发视角的延伸：在面对复杂的嵌套条件判断时，梳理判定表有助于发现逻辑死角，同时可以作为重构和简化判断逻辑的依据。

### 4. 错误推测法
适用场景：基于历史缺陷数据、经验以及对系统底层实现的了解，针对性地设计测试场景。
核心思想：研发人员自带“白盒视角”，最清楚系统中哪些模块最脆弱或逻辑最复杂。

常见推测场景：
*   分页查询接口，传入 `page=0`，`size=-1` 或极端大值（如 `999999`），评估是否会导致内存溢出或慢 SQL。
*   异步消息处理，在消息乱序或重复消费的场景下，业务状态机能否保持一致（幂等性验证）。
*   缓存失效瞬间，大量并发请求穿透到数据库时，是否具备相应的锁机制或限流保护。

### 5. 测试点 ≠ 用例 — 封装规则（Case Packaging，CRITICAL）

上面四种方法推导出的是**测试点**（一个待验证的检查项）。测试点必须先按下面的规则封装成用例，再写入 CSV——用例数既不能少（漏维度），也不能多（同流程重复拆行）。

**Rule P1 — 同流程、仅数据不同 → 合并为一条参数化用例**
两个测试点若满足：同一页面入口 + 相同步骤骨架 + 相同前置条件，仅输入数据不同（如 provider、语言、文件类型、渠道），则它们是**同一条用例**：
- CSV 只写一行；「测试数据」列（col 10）写出变体矩阵（例：`provider ∈ {Deepgram, Cartesia, ElevenLabs, WIZ}`）；步骤写一遍，预期结果对每个变体成立。
- Phase 2 将该行转成一个 `Scenario Outline` + `Examples` 表（每个变体一行 Examples，整个 Outline 仍只挂一个 `@CASE_ID`）。

**Rule P2 — 同一用户旅程上的连续检查点 → 合并为一条多层断言用例**
沿一条连续操作路径出现的检查点（打开弹窗 → 字段可见 → 填值 → 保存 → 重开显示已存值 → 列表列更新）属于**同一条用例**，按顺序断言每个检查点——不要每个检查点拆一条。
「XX 元素可见」单独成条只允许一种情况：该 feature 唯一的一条 @smoke 结构检查。

**P1 vs P3 试金石（「输入数据不同」和「数据准备不同」的区分）**
把用例写成 Given/When/Then：变体差异落在 **When/Then 的参数**里（填的值、选的项、点的行），且同一份 Given/Background 原样不动能跑完所有变体 → 是 P1 的「输入数据」，合并；必须为某个变体**改 Given**（不同角色登录、不同的已有状态、不同 fixture）→ 是 P3 的「数据准备」，拆开。
注意两个边界：① Given 本身只是同一条种子步骤换参数（如 `Given an agent with language "<lang>" is ready`——同一 API、同一句式）不算「准备不同」，仍可参数化合并；P3 针对的是准备**过程/步骤骨架**不同。② 连续旅程中后一步的前置由前一步的动作自然产生（set 完自然「已存在值」再 change/clear）不算「准备不同」，属于 P2 旅程合并。

**Rule P3 — 必须拆开的情形（满足任意一条就拆，优先级高于 P1/P2 的合并）**
- 前置条件 / 数据准备不同（不同 seed 数据、不同角色登录）。
- 预期**行为逻辑**不同，而不只是数据值不同（合法 URL 保存成功 vs 非法 URL 被拒 = 两种行为 → 拆，负向单独成条）。
- 执行方式 / 优先级 / 标签不同（Manual 的运行时日志验证不能并进 Automated 的 UI 用例）。
- 旅程过长掩盖失败定位（步骤 > 8 步，或跨多个页面且各段有独立价值时拆段）。

**自检红线（写 CSV 前必做）**：扫一遍计划的用例清单——若两条用例的标题只差一个名词（provider / 语言 / 页面名），按 P1 合并。目标状态：每条用例要么对应一条独立的行为规则，要么对应一条独立旅程；任何两条用例不共享步骤骨架。

### 6. 覆盖审计表（Coverage Audit — Gate A 的产出物，必须输出）

Phase 1 设计结束时，必须输出下表并让每一行闭合：

| 需求点 / 验收标准 | 维度 | 归属 Case ID |
|---|---|---|
| （逐条列出 PRD/交付文档的需求变更点和验收标准） | Happy / State / Permission / Boundary / Error | VA-XXX-001 |

闭合规则：
- 交付文档的每个变更点和每条验收标准至少映射 1 个 Case ID；
- 五个维度（Happy Path / State Transitions / Permissions / Boundaries / Error Recovery）每个要么有 ≥1 个 Case ID，要么写一句明确的 N/A 理由（如「该功能无状态机 — N/A」）；
- 出现「无 Case ID 且无理由」的行 = Gate A 不通过，回到设计步骤补用例。
