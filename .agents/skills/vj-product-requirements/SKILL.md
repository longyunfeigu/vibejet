# Product Requirements

把模糊的产品想法收敛成一份能交给 `vj-architecture` 和 `vj-plan` 的 PRD，写到
`docs/product/requirements.md`，并配一个可点击的场景原型。

PRD 的主体是给人读的一页纸，回答"为什么做、为谁做、为什么选我们、怎样算做对"。写代码已经很便宜，
所以不在文档里预先定死界面细节，界面交给原型；EARS 只留在 §12 行为合同，给下游 AI 和测试用。

已有成熟 PRD 只想出开发计划、或用户要的是技术方案时不用本 skill（分别交给 `vj-plan` /
`vj-architecture`）。给已有产品加一个不改变押注和非目标的功能，直接用 `vj-plan`。

## 模式

| 模式 | 何时 | 行为 |
|------|------|------|
| `create` | 默认；没有 PRD 或用户要新建 | 跑完整流程 |
| `review` | 用户要审查、找问题 | 按 `references/quality_rubric.md` 出审查报告（分数、问题、缺失决策、交接就绪度、建议修改），用户没要求就不改文件 |
| `update` | 用户要修改、补充 | 在原文件上改，只对变更影响范围补问，保留已有决策、编号和非目标 |

有现成 PRD 但意图不清时，问一句是基于现有文档更新还是重新开始。

## 1. 采访

按 `references/interview_questions.md` 采访。原则是**只问只有用户知道的事**，网上查得到的自己查（第 2 步）。

- 三个问题必须问到，用户要求"直接出草稿"时也一样：证据（问题真的发生过吗）、用户现在怎么应付、
  最小但有价值的版本。另外两个押注问题等第 3 步选方向时再问。用户答不上来的，记为 `[未验证假设]`，不要替用户编。
- 不问显而易见的问题，比如"要不要登录""用什么颜色"。问会改变产品方向的问题。
- 用 `ask_user` 批量问，每轮最多 4 题，每题给选项和推荐默认值；答案先收敛成能写进 PRD 的陈述再问下一轮。
- 用户中途不断扩范围：回到非目标重新确认，新诉求放到后续版本，本轮只收敛 V1。
- 想法和成熟产品正面竞争（"做一个更好的记账 / 健身 / 记卡路里 App"）且用户说不出差异时，建议先走
  `sharpen-idea` 磨定位，不强制。

## 2. 轻量调研

`调研模式`默认值：新产品 0→1 为 `light`；已有产品加功能、内部工具、纯技术债为 `none`。用户可以覆盖，
保密项目不联网。

放在采访之后做：先有自己的问题和押注，再用调研检验它。先看竞品容易被现有功能清单锚定，写出"别人有的我也要有"的 PRD。

`light`：用 `web_search` 看 3-5 个同类产品的官网和用户差评，只回答三件事，每条附来源，写进 §2：
基本功能有哪些、我们的押注有没有人做过、用户最大的不满是什么。多看差评，少看功能清单。
`deep`（用户明确要求时）再加定价、商业模式和壁垒。搜索失败就降为 `none`，相关结论标 `[推断]`。

## 3. 方向原型

先做原型，再写 PRD：只看文字，用户选不出方向；看到能点的成品，才知道自己要什么。

按 `references/scenario-prototype.md`，在动笔写 PRD 之前做 **3-5 个本质不同的产品方向**，每个都是能从头点到尾的
交互原型（不是同一个产品换首页、换配色）。放在同一个文件里用切换条对比，每个方向写清押注、代价和适合谁。
文件放在 `docs/reference/research/designs/prd-{slug}/prototype.html`。

把原型给用户，让用户选一个、混搭几个，或者都不要。这一步问的是方向，不是细节。

**用户选定时，一并问两个押注问题**：为什么选我们、第二次为什么还会回来。押注是选方向时才定下来的，
在这之前问，用户答不出来。按选中方向的押注卡先写好推荐答案，让用户改或认；它们写进 §5.1、§5.2。
用户后来换了方向，这两题跟着重问。

用户选定后，在原型页上标出选中的方向，其余保留作记录；视觉方向定了以后，由 `vj-mock-board` 用正式的
DESIGN.md 画全所有屏幕。

## 4. 一页纸

围绕选定的方向，按 `assets/requirements_template.md` 写 §1-§7，1-2 页写得下。

**给人看的部分要写得像一本好教科书，不是清单**，按 `_shared/vj-skill-conventions.md`「给人看的文档怎么写」。
PRD 特有的两点：读者是懂产品但没参加讨论的人；主线是问题 → 为谁 → 我们押什么 → 用户怎样用 →
怎么知道做对了，后一段建立在前一段上。列表只用于真正并列的条目（如 §3 的角色、§4 的能力清单）。

`范围模式`决定写多少：Lightweight 只覆盖一个核心场景，§2、§6 可以很短；Standard 是默认；Deep 加持久性追问
（见采访题库）和 `deep` 调研。

- 不凑字数、不写"待定"、不编造；不知道的放 §8，需要用户拍板的也放 §8。
- §4 写用户得到什么，不写界面细节和数值阈值。
- §1.1 的指标和 §7 的 eval 要能真的测出来。涉及 AI 输出的能力（识别、生成、推荐），eval 写清样本和过线标准。
- 核心痛点和范围不能互相矛盾：痛点是"坚持不下去"，范围里就得有让人坚持的设计。

## 5. 交接层

写 §8-§12：

- **§10 Architecture Handoff**：非功能约束、数据与权限边界、外部依赖、会影响架构的开放问题。
  不写表、API 路径、框架、部署拓扑。
- **§11 Epic Decomposition Notes**：Epic 顺序与 MVP、依赖、不应拆散的端到端能力、可延后能力、验收风险。
  不按前端/后端/数据库拆。
- **§12 行为合同**：EARS 句式，不超过 12 条，只写最容易漏、出错代价最高的行为——异常用 `If`，持续状态用
  `While`，环境差异用 `Where`，安全和数据边界用 Ubiquitous。下游按句式派生 AC（`If` → Error AC，
  `While`/`Where` → 状态/环境类 Edge AC），所以句式要分对：`If` 只用于真正的失败，状态别写成 `If`。
  主语默认"系统"，不写内部组件名。涉及 AI 输出的能力再附 15-25 个真实输入例子及期望输出，它们就是 eval 的测试集。

需求来源分开标注：`[用户]` / `[调研]` / `[推断]`；证据弱的标 `[未验证假设]`。

## 6. 质量门

1. 跑 `python3 .agents/skills/vj-product-requirements/scripts/validate_prd.py docs/product/requirements.md`。
   规则清单以脚本头注释为准。exit 1 就修完重跑；WARNING 逐条判断。
2. 用 `doc-review` 独立审查 PRD（用户可说"跳过审查"）。表述类意见直接改，改完重跑机检；会改变范围或行为的
   决策类意见不改，留到第 7 步一起问。

## 7. 用户拍板

把 PRD 和原型给用户看，**一次问完**，不分两轮：

- 三桶总结：🟢 用户明确说的；🟡 你推断的、需要确认的；⚪ 明确不做的。
- §8 里所有"待决"项、§11.1 的 MVP 标记、§12 里的具体数值（阈值、时限、边界）。
- 第 6 步审查留下的决策类意见，每条附你的推荐。

这是修正范围最便宜的时机。用户大幅调整时回到对应步骤；确认后把结论写回 PRD，重跑机检。

## 收尾

定稿后跑 `python3 .agents/skills/_shared/scripts/render_doc_html.py docs/product/requirements.md`
生成人读视图（原型会嵌在 §7），之后每次改 PRD 都重跑；渲染失败不阻塞。

## 无人值守

不能提问时照常跑完，不停下等回答：五个必问题按最合理推断写，标 `[未验证假设]` 并列进 §8；原型选证据最强的方向，
其余在 §8 记为待决；第 7 步跳过，推断项标 `[推断]` + Confidence，PRD 状态标"draft · 假设待审批"，
交接状态标"待人工确认"。
