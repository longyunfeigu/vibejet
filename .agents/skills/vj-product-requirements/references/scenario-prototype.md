# 方向原型

PRD 第 3 步用，在写 PRD 之前做。原型是回答问题的、用完就扔的代码：这一版要回答的是"往哪个方向做"。
它不是视觉稿，也不是生产代码。

## 先说清要回答什么

动手前在页面顶部写一行：这批原型要回答的问题。问题决定形态，不要伪造正在被检验的那个维度：

- 判断**流程或状态**（记录一餐要几步、失败后去哪、超标时怎么显示）：必须能真的点着走，状态随操作变化。
  只长得像产品的截图回答不了。
- 判断**长相或信息密度**：必须做到真实的完成度。这类问题通常留给 `vj-design-md-matcher` 和
  `vj-mock-board`，PRD 阶段一般不做。

## 默认做 3-5 个本质不同的方向

- "本质不同"是指押注不同、交互模式不同：比如"极速记录""宽容回顾""对话式记录""不算热量的餐盘法"。
  同一个产品换首页、换配色、换按钮位置不算。三个同一想法的变体是在浪费比较。
- 数量由方向空间决定，不固定为 3；每个方向都要写得出最强版本，写不出的就删掉。
- 每个方向都能从头点到尾（进入 → 核心动作 → 反馈），不是只做一屏。
- 每个方向在页面上写清三件事：押注什么、代价是什么、适合谁。
- 放在同一个文件里，用顶部切换条对比；支持 `?d=<方向>` 直接打开某个方向，方便讨论时互相引用。
- 用户可能混搭（"A 的记录方式 + C 的反馈"），原型要能单独看清每个方向的记录方式和反馈方式。

## 写法

- 单个自包含 HTML 文件：内联 CSS 和 JS，不依赖 CDN，离线能打开。
- **按 PRD 的目标设备做**：Web 应用做成真正的响应式网页，不套手机外壳；手机浏览器优先时用单列布局、最大宽度
  约 440px 居中，并在页面上说明电脑布局另做。原生 App 才用设备外壳。
- 关键状态都能演示：空、加载、失败、超出限制等。页面外放一排"演示控制"按钮，一键切到这些状态。
- 数据是写死的模拟数据，用真实感的内容（真实的菜名、价格、人名），页面上标"模拟数据"。
- 视觉是临时的，页面上标"临时视觉"。用克制的暖色和清楚的层级，不要紫蓝渐变、玻璃拟态这类默认 AI 风格。
- 加一个"复制为 prompt"按钮，把当前方向、当前状态整理成一段文字，用户可以直接贴回对话。

## Web 应用额外要能演示的

- 地址：每个方向、每个主要页面有自己的地址参数，刷新后回到同一处，浏览器后退能返回。
- 键盘：搜索框可以用 `/` 聚焦，回车确认，Esc 关闭弹层。
- 电脑上拍照不现实：桌面宽度下用拖拽上传或粘贴图片代替。

## 验证

交付前用无界面浏览器（如 Chrome headless）截图，至少看桌面宽度和 375px 手机宽度两种；跑一遍每个方向的
点击路径，确认状态变化正确、没有报错。

## 交付后

用户选定方向后，在原型页上标出选中的方向，其余保留作记录。用户的选择写回 PRD（§4 能力、§5 押注与原则、
§8 待决、§12 行为合同）。原型文件留在 `docs/reference/research/designs/prd-{slug}/`，供后续 `vj-mock-board`
和 `vj-plan` 参考；它不是合同，不承载跨 Epic 的约定。
