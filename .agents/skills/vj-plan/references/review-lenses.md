# 计划审查视角

`vj-plan` 第 4 步派独立审查时用（单份 `policy: strict` 或用户要求时；整份 PRD 拆成多份时只审一次，总览加全部计划）。这是可选视角的目录：按风险选几个，
不为"完整"跑满；每个视角只审自己的范围，别人的交给别人。审查对象是计划文档——做什么、关键设计、要拍板的决定、验收清单、执行顺序，都是给人审的。

每条意见的格式：`[N] [Blocking|Non-blocking] [表述|决策] 问题 → 修法 | 证据：计划原文（≤30 字）`。
提不出"照这样做会具体撞上什么"就不报。

| 视角 | 什么时候选 |
|------|-----------|
| 可读性 | 始终 |
| 一致性与可行性 | 始终 |
| 对抗 | 涉及鉴权 / 权限 / 迁移 / 事务 / 幂等 / 并发 / 外部副作用 / AI 输出 |
| 依赖与并行 | 执行顺序 ≥ 5 步，或有决定挡住中间某一步 |
| 界面 | 有新页面 |
| 范围 | 计划拆分了 PRD 的 Epic，或推断出的范围和 PRD 有出入 |
| 跨计划 | 整份 PRD 拆成了多份（这时它是主视角） |

一份普通 strict 计划通常是"可读性 + 一致性与可行性 + 对抗"三个，其余命中才加。

## 可读性

一个懂产品、没参加讨论的人读完计划（先看方案总览和改造前后对比，再看细节），能不能说清：这块要解决什么、数据和状态怎么设计、最危险的地方在哪、
要他拍板什么。Blocking：没有方案总览、读者看不出整体用什么办法；改动现有系统却没有改造前后对比；关键设计只有规则没有场景、读者建立不起心智模型；新表 / 生命周期 / AI 调用缺对应的图；
要拍板的事没写"不定会怎样"；验收清单里混着测试名和状态码，人读不懂。

## 一致性与可行性

各节说的是不是同一套设计：关键设计、决定、验收清单、执行顺序互相对得上，没有一处说 A 一处说 B。
计划里引用的模块、已有实现在仓库里真的存在（用搜索确认，别凭空信）；要求复用的权威实现没被绕开重写。
Blocking：引用不存在的东西导致做不了；关键设计里的行为没有任何验收项；执行顺序做了验收清单之外的事。

## 对抗

质疑关键决定：隐含假设成立吗？被否掉的备选是真被驳倒还是稻草人？高风险流程（权限、迁移、事务、AI 输出、
外部调用）的失败路径有没有写清、有没有验收项兜住？"改到哪些已有东西"有没有漏掉默认了旧行为的已有功能？回滚和不可逆的部分写清没有？"禁止降级"是不是只用在会伪造业务结果或绕过信任边界的地方？
Blocking：关键决定建立在错误前提上；高风险失败路径允许假数据或默认值继续写入；AI 输出没有被系统校验就入库。

## 依赖与并行

执行顺序对不对：共享的数据表、公共结构、页面外壳是不是由第一步先落地；没有依赖的步骤能不能并行；
决定的"挡哪一步"是不是真实依赖——该挡开工的没有被改成挡后面的步骤，也没有为了能开工把决定降级成"上线前定"。

## 界面

每个新页面写清了从哪进、主流程、备选路径、出错路径，以及加载 / 空 / 出错 / 提交中 / 成功 / 无权限状态；
每条路径和状态在验收清单里都有一项。用大白话写，不用设计术语。

## 范围

有没有漏做 PRD 里这块该有的能力，或顺手做了范围外的东西；"不做什么"写清楚没有；延后的能力有没有被偷偷塞进执行顺序。
无人值守写的计划尤其要看：推断出的范围变化必须列在"要拍板的决定"里，不能直接当成已定。

## 跨计划

把总览和全部计划放在一起读：同一张表或同一个服务是不是被两份计划各定义一次；一份计划默认另一份提供了它没写的东西
（字段、接口、返回值）；同一条 PRD 规则没人管，或两份都管且说法不同；同一个数在两处的算法不一致；决定互相矛盾，
或同一条决定在两份里各列一次；`after:` 的先后和真实依赖对不上。Blocking：照着做会让两份计划改同一张表结构互相覆盖，
或某条 PRD 规则在全部计划里都没有验收项。
