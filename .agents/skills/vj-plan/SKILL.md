# vj-plan — 一块工作，一份计划

把"要做的一块东西"写成一份计划：`docs/work/plans/{date}-{slug}.md`，按 `assets/plan.template.md`。
一块是一两天能做完、能单独验收的东西（如"一句话记一餐"）。

计划只写人要审、AI 推不出来的东西：做什么不做什么、难以回头的设计、要用户拍板的事、怎样算做完、先做什么后做什么。
不写"先读哪些文件、改哪些文件、跑什么命令"——执行的 AI 开工时会重新读代码，提前写的文件清单在前置计划没做完时
写不准，写准了也会过时。把验收变成测试、拆成子任务是 `vj-work` 开工时的事。

固定的只有三节："要你拍板的决定""验收清单""执行顺序"，因为脚本要读它们算出能不能开工、验收有没有漏。
其余内容按这块工作的性质写，标题自己起：数据为主的块讲数据和状态，有页面的块讲交互，调用模型的块讲失败路径，
测试性质的块讲测什么、过线标准、结果怎么用。用不上的不写。

不适用：一两个文件的小改动（`vj` 直接改）；还说不清做什么、为谁做（先 `vj-product-requirements`）。

## 输入是整份 PRD 时

先拆，再写。按 PRD §4 的 Epic 和 §11 的顺序拆；一个 Epic 包含两组互不相干的能力（如"不用 AI 的搜索记录"和
"要等 AI 测试过线的一句话记录"），或者验收清单会超过约 40 项，就再拆成几份（`2a`、`2b`）。开发前要先跑的测试
（PRD §7）不依赖任何代码时单独成一份，好让它和第一块并行立刻开跑。

拆完先写**拆分总览** `docs/work/plans/{date}-epic-0-overview.md`（frontmatter `type: plan-overview`），
再写各份计划。总览给人看拆分是否合理，也是各份计划共同的约定，写清：

- 几份、每份覆盖 PRD 哪些能力和行为规则、谁等谁（`after:`）、为什么这样拆；
- 共享的东西谁落地：数据表、公共服务、页面外壳和导航由最先需要它的那份落地，别的计划只引用；
- 第一屏：一张"要你拍板"汇总表，把各份计划里的 `待你定` 按影响排好（问题、推荐、挡哪份计划哪一步），
  读者不用打开 8 份计划就知道要定什么；
- 每条决定归哪份计划，其余计划只引用不重复列；
- PRD 例子表里每一句归哪份验收；
- 跨计划的口径：同一个数在两处怎么算才一致、可扩展的字段（如"用途"）后续计划怎么加值。

各份计划文件名 `{date}-epic-{编号}-{slug}.md`，编号让它们在目录里按顺序排。每份都现在写完——计划里没有要等
代码才能写的东西，`after:` 只表示先后。

## 1. 读

- 输入是 PRD 章节时：读这块对应的能力、§5.3 原则、§6 约束、§7 开发前验证、§10、§12 行为合同和例子表。
- 输入是一句功能描述时：读相关代码和现有计划；PRD 存在就读，用来对齐原则和非目标。
- 跑 `python3 .agents/skills/vj-plan/scripts/scout.py --domains <业务域> [--frontend]`，几秒拿到架构基线、
  现有接口 / 数据合同（`docs/project/api|data|ui/`）、可复用实现和 `docs/solutions/` 里的经验，只精读命中的文件。
- 有页面时读 `docs/project/DESIGN.md`；缺失就把"先定视觉方向（`vj-design-md-matcher`）"列成待拍板的决定
  （整份 PRD 时只在最先做页面的那份列），不在计划里自己补审美。

## 2. 追问（开场）

计划写出来之前，先把会让计划走样的事问清楚。不问就写，推断会堆成几十条"待你定"，人得逐份翻计划去找（食衡第一次
整份 PRD 出计划时，8 份计划堆了 50 条）。读完、拆完（整份 PRD 时总览草稿已有）之后，先列出所有推断，按下面的标准分两类：

- **要问的**：推断错了会改变范围（做不做某个能力）、改变用户看得到的行为（页面上出现什么、数字怎么算、什么时候提醒），
  或者做了很难回头（数据删不删、存不存历史、选哪个外部服务）。
- **不问的**：常数、命名、实现手法、选什么库，以及 PRD 已经写了的。按最合理的写，记进计划的"我按这些假设写的"清单，
  每条带 Confidence: H/M/L；不进决定表，不挡开工。上线前必须有人拍板、但不挡开发的事（法务定保留期限、营养师确认下限、
  产品定成本上限的数值）进决定表，标 `上线前定`。

要问的按影响从大到小，用 `ask_user` **一次问一个**：每问写成一句大白话的问题、不定会怎样、推荐和理由，用户可以只回
"按推荐"。上一问的答案会改变后面的问题时，先改再问下一个。问到没有"要问的"为止；用户说"够了 / 剩下按推荐"就停，
剩下的按推荐写，状态 `已定`，推荐列开头写"按推荐，未逐条确认"。答完的写进对应决定，状态 `已定`。

输入只有一句功能描述时，谁用、什么场景、核心要做什么、明确不做什么，说不清的先问。
整份 PRD 也只有这一轮追问，所有计划合起来问，不每份计划各问一轮。

## 3. 写

按 `_shared/vj-skill-conventions.md`「给人看的文档怎么写」：开头一句话说清这份计划要读者做什么决定，
用一个贯穿的使用场景讲机制，每个设计取舍讲到"不这样会怎样"。

计划先总后分：做什么、为什么 → 方案总览 → 关键设计 → 改到哪些已有东西、风险和回滚 → 假设 → 决定 → 验收 → 执行顺序。
读者先看到"整体用什么办法、系统从什么样变成什么样"，再进细节；细节不平铺成一排二级标题，收进"关键设计"下面。

- **做什么、为什么**：几句话，链接回 PRD 或写明来源；明确不做什么。
- **方案总览**：一句话方案（这次整体用什么办法），再一段总体思路（为什么这样、主要取舍），不列文件和细节。
  改动现有系统时紧跟一张**改造前后对比**：只画到组件这一级，之前什么样、之后什么样（Mermaid 流程图或前后两段示意），
  纯新增、没有"之前"的部分只出现在"之后"里。只做新东西、不碰现有系统时不画对比。
- **关键设计**：下面按这块实际有的起三级小节（如"数据怎么存""每日目标怎么算""删除账户""页面怎么交互"），
  讲数据怎么存、状态怎么变、主流程怎么走。
  新增或修改数据表 → 画实体关系图；有生命周期的对象 → 画状态图；调用大模型或外部服务 →
  画时序图并画出超时 / 失败分支（图用 Mermaid，规则见 conventions「图规范」）。
  写清信任边界和必须复用的已有实现（鉴权、响应信封、API client 等不重写）。
  做非平凡能力前先花几分钟查有没有现成的库或方案（能联网就用 `web-access` 快查；查不了就写明、置信度标中），
  结论写成"直接用 / 改造 / 自研和理由"：选库这类实现手法写进"我按这些假设写的"；要花钱或很难回头的
  （选外部服务、买数据授权）才进决定表。
- **页面怎么交互**（有页面时，作为关键设计下的一个小节）：用大白话写每个页面从哪进、用户做什么、看到什么——主流程、备选路径、出错路径
  各走一遍（可以画流程图），加上要覆盖的状态：加载中、没有数据、出错可重试、提交中、成功、无权限、内容过长。
  不做可点击的 mock，不写屏型、富度这类设计术语。
- **接口约定**（同时有前端和后端时，作为关键设计下的一个小节）：每个新增或改动的接口写路径、请求字段、返回字段、
  会返回哪些错误码和各自含义。它是前后端之间的合同：`vj-work` 先把它落成代码里的数据结构，前端照它用模拟数据做，
  后端同时实现，不用等后端做完。只写对外能看到的形状，不写内部实现。
- **改到哪些已有东西、风险和回滚**（改动现有系统时必写）：逐条写碰到的已有功能和**要变的旧假设**——现在默认什么、
  改完变成什么、怎么处理（如"用户查询一直默认只有软删除 → 新增真删只给删除账户用"），用行为语言写，不写文件行号
  （行号要读代码才写得准，`vj-work` 开工时补）；再写副作用和风险（不接受"没有副作用"），最后写怎么回滚、哪些不可逆。
  **测试也算已有东西**：现有单元测试、AutoTest 的用例和公共步骤（如登录准备脚本、按旧页面写的定位）依赖了要变的旧行为时，
  同样列进表里（食衡 Epic 1 删掉占位首页时漏列了 AutoTest 的登录准备，整个端到端套件起不来）。
  不这样写，执行时最常出事的地方——默认了旧行为的已有代码和测试——在计划里就是隐形的。
- **要你拍板的决定**：每条写成一句大白话的问题、不定会怎样、推荐、挡哪一步。状态只用四个：
  `待你定`、`待证据`（只能靠真实测试回答，如 AI 能不能听懂）、`上线前定`（不挡开发）、`已定`。
  "挡哪一步"写真实依赖：`不挡`、`开工`，或执行顺序里的`第 N 步`。不要为了让计划能开工去改决定的状态或
  挡的步骤——挡就是挡，状态自然会是 `awaiting-approval`。
- **验收清单**：这块做完要过的全部检查，按场景分组。写法和必测项见 `references/checklist-design.md`。
  它是"该测哪些"的覆盖来源：AI 写代码时先把它变成测试，`prd-to-bdd` 生成用例时以它为准不漏项。
  人把关看的是下面生成的用例表，不是这张清单。
- **执行顺序**：编号列表，每一步是一个切片——一块能单独证明做对的能力（按能力拆，不按前端 / 后端机械拆）。
  同一模块、数据库迁移前后紧挨着的合成一步，不拆成两步（拆开只会让执行时多读一遍代码）。每步写一行标注：
  会不会加数据库迁移、会不会改共享的注册文件（路由总表、依赖注入、模型清单这类多个任务都要往里加一行的文件）、
  和哪几步可以并行、要等哪个决定或哪份前置计划。加迁移的步骤之间、改同一个注册文件的步骤之间只能串行；
  有接口约定时，前端的步骤写明"接口约定落地后和后端并行"。`vj-work` 照这些标注排顺序，不再现场分析。
  有 `待证据` 的决定时，加一步证据步骤：只写 `.vj/` 和 `docs/reference/research/`，过线标准直接用 PRD §7 写的
  （如"100 句里食物正确率 ≥85%"）；等它的步骤在证据回来之前不开工。证据由另一份计划产出时不重复加证据步骤：
  决定里写明由哪份计划回答，那份计划写进 `after:`。`已定` 和 `上线前定` 的决定不挡开发，"挡哪一步"写 `不挡`。

### 生成测试用例（调 `prd-to-bdd`）

有运行时行为的计划（有页面或接口），验收清单写完就用 `invoke_skill` 调 `prd-to-bdd` 为这一块生成用例；只做测试、调研或文档、
没有运行时行为的计划（如开发前的模型测试）跳过。人把关看它产出的中文用例表——每行一个场景，标题说清测什么，前置条件、
测试数据、步骤、预期分列写，人读得快、判断得了对错和要不要补。`prd-to-bdd` 按它自己的规则写，**不改它的写法**；
调用时只交代四件事：

- 输入：PRD 加这份计划（计划顶替它原本读的交付设计文档，补上 PRD 不会写的设计层风险，如事务、凭证失效、绕过页面提交）；
- "需求/缺陷编号"列填这份计划的文件名（不带 `.md`）；
- 每行"备注"写"对应验收：A5、A6"，一行可以对应多条验收，计划里每条验收至少进一行；页面和接口都看不到、只能在后端
  内部验证的规则也进，执行方式标 `后端单测`，备注写明由哪个后端测试覆盖；
- 代码还没有，所以自动化用例都进待激活的 `.pending.feature`，不写页面对象和步骤。

生成后把用例目录写进计划 frontmatter `cases:`（如 `AutoTest/modules/diet`），然后跑
`python3 .agents/skills/_shared/scripts/plan_case_trace.py <计划文件>`：有验收没对上用例就补用例；
它列出的"用例有、计划没有"的行多半是 PRD 兜底补出来的，看情况回填进验收清单。

整份 PRD 时，每个写计划的子代理写完自己那份就立刻生成，不等其他计划；`npm run bdd:gen`、`typecheck`、`lint:bdd`
（在 `AutoTest/` 下）等全部回来后统一跑一次。

命中 `AGENTS.md`「Plan 规范」的 strict 触发条件时，frontmatter 写 `policy: strict`。

整份 PRD 拆成多份时，总览写完后每份计划派一个子代理并行写（`spawn_agent`；交代 PRD 路径、总览路径、
这块的范围、模板和本 skill 路径；写完计划接着按上一节生成用例）。紧密耦合的两份（后一份直接建在前一份的表上）可以交给同一个子代理。
全部回来后自己通读一遍，查各份之间的冲突：同一张表定义了两次、决定互相矛盾、同一条 PRD 规则没人管或两份都管、
一份计划默认另一份提供了它没写的东西。冲突改在计划里，影响约定的同步改总览。

## 4. 检查与交付

1. `python3 .agents/skills/_shared/scripts/plan_lint.py <计划文件>`（固定三节、决定状态、挡哪一步、验收格式、前置计划、
   用例目录）和 `python3 .agents/skills/_shared/scripts/plan_case_trace.py <计划文件>`（验收逐条对上用例）。
   有 ERROR 修完重跑。审查或改决定后验收变了，重调 `prd-to-bdd`（它自带去重，只补新增的）再跑核对。
2. 独立审查（`doc-review`，视角从 `references/review-lenses.md` 按风险选）：单份计划在 `policy: strict` 或用户要求时派一个；
   整份 PRD 拆成多份时只派一次，审总览加全部计划，重点是跨计划视角。表述类意见直接改，会改范围或行为的并进
   对应计划的"要你拍板的决定"。
3. 状态：有 `待你定` / `待证据` 的决定挡开工或挡第 1 步 → `awaiting-approval`；否则 `ready`。
4. 跑 `python3 .agents/skills/_shared/scripts/render_doc_html.py <计划文件或目录>` 生成网页。
5. 告诉用户打开哪个网页、要他把关哪几张用例表（给出 CSV 路径）、要他拍板哪几条（只列 `待你定`），下一步是 `vj-work`。
   拆成多份时列一张表：每份文件、做什么、等谁、用例表在哪、现在能不能开工。

## 无人值守

不能提问时照常写完，不停下等：第 2 步"要问的"写进决定表标 `待你定` 并给推荐；"不问的"写进"我按这些假设写的"。
整份 PRD 时把全部 `待你定` 汇总到总览第一屏，顺序就是下次追问的顺序。
